Branch ve pull request

18:45–21:15 · 2 dk 30 snSlayta git ↗

Şimdi bugünün en önemli fikri. Üstteki kalın çizgi main: robotta her zaman çalışan sürüm. Kural şu: main bozulmaz. Yeni bir şey denemek istediğinizde, mesela ultrasonik sensör eklemek için, main'den bir yan yol açarsınız; buna branch denir. Bir: tek bir özellik ya da düzeltme için branch açın. İki: o branch üzerinde istediğiniz kadar commit yapın; main bu sırada güvende ve takım arkadaşlarınız robotu çalışan sürümle kullanmaya devam ediyor. Üç: iş bitince bir pull request açın; yani “bu değişikliği main'e katmak istiyorum, şunu şu nedenle değiştirdim” deyin. Dört: bir takım arkadaşınız inceler, uygunsa main'e birleştirilir; buna merge denir. Kapaktaki çizim tam olarak buydu. GitHub'daki iş birliğinin tamamı bu dört adımın tekrarı.

Diff okumak

21:15–22:15 · 1 dkSlayta git ↗

Pull request'i incelerken baktığınız şeye diff denir: neyin değiştiğini gösteren fark. Kırmızı, başında eksi olan satırlar silinmiş; yeşil, başında artı olan satırlar eklenmiş. Bu örnekte biri Arduino Uno'yu ESP32 ile değiştirmiş ve motor sürücü pinlerini eklemiş. Bunu her pull request'in Files changed sekmesinde görürsünüz. Alışkanlık edinin: merge etmeden önce diff'i okuyun; her seferinde, kendi pull request'iniz olsa bile.

Eğitmen için: Hello World gösteriminde Files changed sekmesini açacağınızı söyleyin.

Pull request incelemek

22:15–23:45 · 1 dk 30 snSlayta git ↗

Diff'i okudunuz; şimdi yorum yazacaksınız. Soldaki yorum işe yaramaz: “Burası yanlış.” Neden yanlış, ne yapmak gerek? Sağdaki işe yarar: “D5 pini docs/pins.md'de zaten encoder için ayrılmış. Motoru D9'a alabilir miyiz?” İyi bir review yorumu dört şeydir: kibar, somut, bir satıra bağlı ve gerekçeli. Yorumu bitirince üç karardan birini verirsiniz. Comment: sadece yorum, henüz karar yok. Approve: uygun, birleştirilebilir. Request changes: birleştirmeden önce düzeltilmesi gereken bir şey var. Sanayide kod incelemesi de tam olarak böyle yapılır.

Merge conflict: panik yok

23:45–26:15 · 2 dk 30 snSlayta git ↗

Bu ekranı ilk gördüğünüzde korkacaksınız; o yüzden şimdi, sakin bir anda görüyoruz. Buna merge conflict, yani çakışma denir. Ne oldu? İki kişi aynı dosyanın aynı satırını farklı biçimde değiştirmiş: biri Kp'yi 1.4 yapmış, diğeri 1.8. Git hangisinin doğru olduğunu bilemez; o yüzden kararı size bırakır ve iki sürümü işaretlerle gösterir. Küçüktür işaretlerinden eşittir çizgisine kadar olan kısım sizin branch'iniz; eşittir çizgisinden büyüktür işaretlerine kadar olan kısım gelen değişiklik. Çözüm üç adım. Bir: hangi değer doğru? Takımla konuşun ya da robotta deneyin; bu bir mühendislik kararı, Git'in kararı değil. İki: işaret satırlarını silin, doğru satırı bırakın. Üç: kaydedin ve commit edin. Bu kadar. Önlemek için: sık sık pull yapın, branch'leri küçük tutun ve aynı dosyada aynı anda çalışmayın.

Eğitmen için: İşaret satırları silinmezse kodun derlenmeyeceğini ekleyin.

Sık hatalar ve çözümleri

28:00–30:00 · 2 dkSlayta git ↗

Bu bölümü sık hatalarla kapatalım; hepsini bir gün yaşayacaksınız. Push reddedildiyse GitHub'da sizde olmayan commit'ler var demektir: önce pull, sonra tekrar push. Commit mesajında yazım hatası yaptıysanız ve henüz push etmediyseniz commit --amend ile düzeltirsiniz. Yeni bir commit robotu bozduysa revert ile o commit'i geri alırsınız. Revert geçmişi silmez; üstüne “geri alındı” diye yeni bir kayıt ekler, bu yüzden ortak çalışmada güvenlidir. Şifre repoya gittiyse önce şifreyi değiştirin, sonra dosyayı .gitignore'a ekleyin. “File too large” hatası alırsanız: GitHub 100 MB üstü dosyaları kabul etmez; büyük dosyalar için Git LFS ya da Release kullanılır. Commit'leriniz profilinizde görünmüyorsa Git'teki e-posta hesabınızdakiyle eşleşmiyordur. Bu tabloyu ezberlemeyin; takıldığınızda dönüp bakın.

Güvenli ajan iş akışı

31:45–33:45 · 2 dkSlayta git ↗

Bir ajanla güvenli çalışmanın altı adımı var; fark edeceğiniz gibi bunlar az önce konuştuğumuz GitHub akışının aynısı. Bir: bir issue'dan başlayın; ajana ne yapacağını yazılı bir görevle verin. İki: yeni bir branch açın; ajan asla main'de çalışmasın. Üç: önce açıklatın ve plan yaptırın, sonra kod yazdırın. Dört: ajanın yaptığı her değişikliğin diff'ini kabul etmeden okuyun.
