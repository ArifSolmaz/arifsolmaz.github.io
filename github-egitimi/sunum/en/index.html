TWO DIFFERENT THINGS

Git vs GitHub

GIT

The tool on your laptop

  • Tracks every change to your files
  • Keeps a full history you can rewind
  • Merges teammates' work safely
  • Runs locally, even offline

Like a camera: it takes snapshots of your project.

GITHUB

The website in the cloud

  • Hosts your repositories online
  • Issues, pull requests, project boards
  • Access control for your team
  • A public portfolio of your work

Like a shared album for those snapshots.

GitHub is built on Git — you use both together.

GitHub for Mechatronics Engineers

05

These two names sound the same but are different things. Git is a free program that records the history of a folder on your computer, like a camera taking snapshots. GitHub is a website that stores those snapshots online, like a shared photo album, and adds tools for teamwork. Today we only use the GitHub website, so you don't need to install Git yet.

Every commit has a message. Write it for the person who reads it next month — probably you. Start with a verb and say what changed: 'Fix left motor spinning backwards' is useful, 'update' is not. Small, frequent commits are easier to understand and to undo than one big commit at the end of the week.

PART 1 · HABITS

What stays out of the repo

Secrets

Wi-Fi passwords, API keys, tokens. Once pushed to a public repo, treat them as leaked.

Build output

Compiled .hex and .bin files, .pio/, __pycache__/ — they can be rebuilt from source.

Huge binaries

Videos and large CAD assemblies bloat history. Use Git LFS, or attach them to a Release.

# .gitignore

.pio/

build/

*.hex

secrets.h

GitHub for Mechatronics Engineers

14

Some files must never go on GitHub. Passwords and keys: if your public project contains your Wi-Fi password, anyone can read it, and deleting it later does not remove it from the history. Build files: they are created automatically and just take space. Very big files like videos: GitHub refuses files over 100 MB. Listing them in .gitignore makes Git skip them.

Branches and pull requests

1 · Branch

Start a branch for one feature or fix.

2 · Commit

Work on the branch; main stays safe.

3 · Pull request

Ask to merge; explain what and why.

4 · Review, merge

A teammate reviews, then it joins main.

GitHub for Mechatronics Engineers

17

main is the version that works on the real robot, so you don't experiment on it. Instead you create a branch: a separate copy where you can change things freely. When your change works, you open a pull request to ask for it to be joined into main. A teammate looks at it, and then it is merged. If the experiment fails, you just delete the branch — main was never touched. In Learn Git Branching, the Branching and Merging levels show this as a growing tree.

PART 2 · REVIEWING CHANGES

Reading a diff

README.md

+2 −1

# Line Follower Robot

− Uses an Arduino Uno.

+ Uses an ESP32 DevKit.

+ Motor driver: L298N on pins D5/D6.

## Wiring

− Red lines with − were removed.

+ Green lines with + were added.

You see this on the Files changed tab of every pull request, and on every commit.

Read the diff before you merge — every time, even your own.

GitHub for Mechatronics Engineers

18

A diff shows exactly what changed between two versions of a file. Red lines starting with − were removed, green lines starting with + were added, grey lines are unchanged and only there for context. You will see diffs on every pull request (the Files changed tab) and on every commit. Always read the diff before accepting a change, even your own.

PART 2 · REVIEWING CHANGES

Reviewing a pull request

✗ NOT HELPFUL

“This is wrong.”

✓ HELPFUL

“Pin D5 is already used by the encoder in docs/pins.md. Could we move the motor to D9?”

Good review comments are kind, specific, tied to a line, and give a reason.

Comment

General feedback, no decision yet.

Approve

Looks good — ready to merge.

Request changes

Something must be fixed before merging.

GitHub for Mechatronics Engineers

19

Reviewing means reading someone's pull request and giving feedback before it is merged. Good comments are kind, specific, point to a line, and explain why. 'This is wrong' does not help; 'Pin D5 is already used, could we use D9?' does. When you finish a review you choose: Comment (just feedback), Approve (ready to merge) or Request changes (something must be fixed first).

PART 2 · COLLABORATION

Merge conflicts: don't panic

// firmware/main.ino

<<<<<<< HEAD

const float Kp = 1.4;

=======

const float Kp = 1.8;

>>>>>>> feature/pid-tuning

What happened? Two people changed the same line differently; Git can't decide which one is right.

1 · Which value is correct? Ask the team, or test on the robot.

2 · Delete the markers, keep the right line.

3 · Save, commit, push.

Prevention: pull often, keep branches small, don't edit the same file at the same time.

GitHub for Mechatronics Engineers

20

A merge conflict happens when two people changed the same line in different ways. Git can't guess which one is right, so it shows both and asks you to choose. The part under HEAD is your version, the part under ======= is the other one. Keep the correct line, delete the marker lines (<<<, ===, >>>), and save. It's not an error, just a question. To practise, GitHub Skills has a short free course called Resolve merge conflicts.

GitHub for Mechatronics Engineers

23

Everyone makes these mistakes in the first weeks — that's fine. If GitHub refuses your push, someone else saved first: get their changes (pull), then try again. If a new change broke the robot, revert creates a new snapshot that undoes it.
