Sound familiar?

1:15–2:45 · 1 min 30 sGo to slide ↗

Look at this folder: robot_code, robot_code_v2, v2_WORKING, v3_final, v3_final_REALLY… and finally teacher_fix. Who has a folder like this on their laptop? Yes — almost all of us. This is actually version control, just done by hand, and done badly, because it can't answer three questions. Which file is on the robot right now? What exactly changed between v2 and v3? Who broke the motor code, and when? A tool called Git answers all three. GitHub puts those answers online and shares them with the whole team. The rest of today is just those two sentences, unpacked.

Instructor cue: Ask for a show of hands and wait for the laughter; the point of this slide is recognition. Read the three questions slowly.
04

What is GitHub?

2:45–4:00 · 1 min 15 sGo to slide ↗

So what exactly is GitHub? In GitHub's own words: a cloud platform that supports the whole development process, from planning the work to shipping and maintaining it. We can boil that down to three verbs. Store: it keeps your code, firmware and documents with their full history. Plan: you track tasks, bugs and deadlines. Share: you work with teammates and show your work to the world. Don't let the word "software" put you off. For us, software means Arduino code, control algorithms and simulations — and wiring diagrams, CAD files and reports can live in the same repository.

Instructor cue: The definition comes from the GitHub Docs page "What is GitHub?".
05

Git vs GitHub

4:00–5:30 · 1 min 30 sGo to slide ↗

This is the most common mix-up, so let's go slowly. Git and GitHub are two different things. Git is a free program that runs on your computer. It tracks every change in a folder and keeps a full history you can rewind, and it works offline. Think of it as a camera: it takes snapshots of your project. GitHub is a website. It is like a shared photo album that stores those snapshots online, and it adds tools for teams: issues, pull requests, boards, and control over who can access what. GitHub is built on top of Git, and you use them together. There are similar sites, like GitLab and Bitbucket, and they use Git too. The good news: to get started you don't need to install Git at all; the GitHub website is enough.

Instructor cue: You will ask for the "Git is the camera, GitHub is the album" image again in the quiz on slide 30.
06

Eight words you need today

5:30–6:30 · 1 minGo to slide ↗

We will use eight words today. Don't memorise them; each one comes back with an example in a minute. A repository, or repo: a project folder plus its whole history. A commit: a saved snapshot with a message. A branch: a parallel line of work. Push and pull: send to GitHub, and get from GitHub. Clone: copy a repository onto your computer. An issue: a task, bug or idea that you track. A pull request: a proposal to merge a branch. And the README: the front page of a repository.

Before you start: setup

7:15–8:15 · 1 minGo to slide ↗

You need three things to start. One: a free account on github.com. Choose your username carefully, because it will appear on your CV and in your email signature, so use your real name rather than a nickname. Two: a tool. If you're new, GitHub Desktop works with buttons; if you like the command line, use Git itself. Three: tell Git who you are, once — that's what the commands in the black box do. The one critical point here: the email you give Git must match the one on your GitHub account, otherwise your work won't show up on your profile. None of this is required to get started, though; the browser is enough.

10

Anatomy of a mechatronics repo

8:15–9:45 · 1 min 30 sGo to slide ↗

What does a mechatronics repository look like? The tree on the left is a typical line-follower robot. At the top is README.md, the front door: what the project is, how to wire it and how to run it. It's the first thing anyone sees when they open your repository. The firmware folder holds the microcontroller code: Arduino, ESP32, STM32. The electronics and cad folders hold schematics, PCB files and 3D parts, and docs holds wiring photos. There is also a .gitignore file, a list of files Git should never track; I'll come back to it in a few slides. In short, GitHub is not only for code — it's for every file in a project.

Instructor cue: Ask students to picture their own course or capstone project in this structure.
11

Markdown in two minutes

9:45–11:00 · 1 min 15 sGo to slide ↗

README files are written in a simple language called Markdown. On the left is what you type; on the right is what GitHub shows. A hash sign makes a heading, and two hashes make a smaller heading. A dash at the start of a line becomes a bullet point. Text between two pairs of asterisks appears in bold. An exclamation mark, square brackets and round brackets add an image. The line at the bottom covers almost every README. In a word processor you format with menus; here you do the same job with a handful of symbols.

Instructor cue: Mention that you will open the Preview tab while editing the README in the Hello World demo.
12

The everyday loop

11:00–13:15 · 2 min 15 sGo to slide ↗

Now the heart of it: the everyday loop. There are four steps. One: you edit your files — say you change the motor code. Two: you choose which changes to save; that's called add, or staging. Three: commit — you take a snapshot with a message. These three steps happen on your own computer. Four: push — you send those snapshots to GitHub, and only then can your team see them. Keep this distinction in mind: commit saves, push shares. If you commit but leave the lab without pushing, the work stays on your laptop. The commands at the bottom are the written form of these steps once you install Git; for now, just recognise them. In the browser, a single button — Commit changes — does all of this for you. If you want to see it on a live tree, the first level of Learn Git Branching is exactly this.

Instructor cue: Point at the four boxes in order. Have the class repeat "commit saves, push shares".
13

Commit messages for future you

13:15–15:15 · 2 minGo to slide ↗

Every commit has a message, and you are really writing it for your future self. Look at the left: update, fixed stuff, asdf, final version FINAL. Two weeks from now, when the robot starts oscillating, none of these will help you. The ones on the right will: Add HC-SR04 ultrasonic sensor driver; Fix left motor spinning backwards; Lower PID Kp from 2.0 to 1.4. Look at that last one: if the robot starts oscillating, it tells you exactly what to undo. The rule is simple: start with a verb, and say what changed and why. And make each commit one logical change — don't fix the motor and the display in the same commit.

Instructor cue: You can ask: "Which column would your last commit message go in?"
14

What stays out of the repo

15:15–17:00 · 1 min 45 sGo to slide ↗

Some files should never go into a repository. First, secrets: Wi-Fi passwords and API keys. Pushing your home Wi-Fi password to a public repository is a classic ESP32 mistake. If a password was ever pushed to a public repository, treat it as leaked and change it, even if you delete it later, because it stays in the history. Second, build outputs: .hex and .bin files and build folders. They can be regenerated from the source, so there's no need to store them. Third, huge files: videos and large CAD assemblies bloat the history. You list all of these in the .gitignore file, like the example on the right, and Git ignores them. A common pattern for passwords: keep the real values in secrets.h and ignore it, and commit a secrets_example.h with empty values instead.

Managing a team project

17:00–17:15 · 15 sGo to slide ↗

Part two: team projects. How does a team of four build one robot without chaos?

16

Issues: one task, one ticket

17:15–18:45 · 1 min 30 sGo to slide ↗

The first tool for teamwork is the issue. An issue is one piece of work you track: a bug, a task or an idea. The example here is issue number 12: "Left motor stalls at low PWM." It has labels — bug, hardware, high priority. It's clear who it's assigned to and which milestone it belongs to, and there's a checklist underneath. Compare that with "motor's broken again" in the team WhatsApp group: that message is gone in three days, while this record stays. Four rules: one problem per issue; a title a stranger could understand; labels and an assignee, so nobody has to guess who owns it; and when the work is done, close it by writing "Fixes #12" in a commit or pull request.

Instructor cue: Stress the number (#12); the "Closes #7" question on slide 30 builds on it.
17

Branches and pull requests

18:45–21:15 · 2 min 30 sGo to slide ↗

Now the most important idea of the day. The thick line at the top is main: the version that always works on the robot. The rule is: main never breaks. When you want to try something new — say, adding an ultrasonic sensor — you open a side path from main, called a branch. One: create a branch for a single feature or fix. Two: commit as much as you like on that branch; main stays safe, and your teammates keep using the working version on the robot. Three: when you're done, open a pull request — you say, "I'd like to bring this change into main; here is what I changed and why." Four: a teammate reviews it, and if it's good, it gets merged into main. That is exactly the drawing on the cover slide. All collaboration on GitHub is these four steps, repeated.

Instructor cue: Don't rush this slide; these are the most important minutes of the lecture. Refer back to the drawing on the cover slide.
18

Reading a diff

21:15–22:15 · 1 minGo to slide ↗

When you review a pull request, what you look at is called a diff: the difference that shows what changed. Red lines starting with a minus were removed; green lines starting with a plus were added. In this example someone replaced the Arduino Uno with an ESP32 and added the motor driver pins. You see this on the Files changed tab of every pull request. Make it a habit: read the diff before you merge — every time, even if it's your own pull request.

Instructor cue: Mention that you will open the Files changed tab in the Hello World demo.
19

Reviewing a pull request

22:15–23:45 · 1 min 30 sGo to slide ↗

You've read the diff; now you write a comment. The one on the left doesn't help: "This is wrong." Why is it wrong, and what should change? The one on the right helps: "Pin D5 is already used by the encoder in docs/pins.md. Could we move the motor to D9?" A good review comment is four things: kind, specific, tied to a line, and backed by a reason. When you finish, you choose one of three decisions. Comment: just feedback, no decision yet. Approve: looks good, ready to merge. Request changes: something must be fixed before merging. This is exactly how code review works in industry.

20

Merge conflicts: don't panic

23:45–26:15 · 2 min 30 sGo to slide ↗

The first time you see this screen you'll be scared, which is why we're looking at it now, calmly. It's called a merge conflict. What happened? Two people changed the same line of the same file in different ways: one set Kp to 1.4, the other to 1.8. Git can't know which one is right, so it leaves the decision to you and shows both versions between markers. The part from the less-than signs down to the line of equals signs is your branch; the part from the equals signs down to the greater-than signs is the incoming change. The fix is three steps. One: which value is right? Talk to the team or test on the robot — that's an engineering decision, not Git's. Two: delete the marker lines and keep the right line. Three: save and commit. That's all. To prevent conflicts: pull often, keep branches small, and don't edit the same file at the same time.

Instructor cue: Add that the code won't compile if the marker lines are left in.

23

Common mistakes and fixes

28:00–30:00 · 2 minGo to slide ↗

Let's close this part with common mistakes — you will all hit these one day. If a push is rejected, GitHub has commits you don't have yet: pull first, then push again. If you made a typo in a commit message and haven't pushed yet, fix it with commit --amend. If a new commit broke the robot, undo it with revert. Revert doesn't delete history; it adds a new commit that says "undone", which is why it's safe in shared work. If a password got pushed, change the password first, then add the file to .gitignore. If you get "File too large": GitHub refuses files over 100 megabytes, so use Git LFS or a Release for big files. And if your commits don't appear on your profile, the email in Git doesn't match your account. Don't memorise this table; come back to it when you get stuck.

25

Claude Code and Codex

30:15–31:45 · 1 min 30 sGo to slide ↗

A coding agent is not just a chatbot that answers questions. It's an assistant that runs in your terminal, reads and edits your files, and runs commands. Here are the two best-known ones: Anthropic's Claude Code on the left and OpenAI's Codex CLI on the right. Each installs with one command and runs inside your project folder. Both need a paid subscription or an API account. Both have a project rules file: CLAUDE.md for Claude and AGENTS.md for Codex, where you write rules like "our board is an ESP32; never change pins without asking". And both can work inside GitHub, when you tag them in an issue or a pull request. The important part comes on the next slide: using them safely.

Instructor cue: Install commands change over time; point students to the docs listed on the slide.
26

The safe agent workflow

31:45–33:45 · 2 minGo to slide ↗

There are six steps to working safely with an agent, and as you'll notice, they are the same GitHub workflow we just covered. One: start from an issue, so the agent gets a written task. Two: create a new branch; never let an agent work on main. Three: ask it to explain and plan first, and only then to write code. Four: read the diff of every change it makes before accepting it. Five: test on the real robot — this one is not negotiable. Six: push, open a pull request and get a human review. The example on the right shows these steps: a branch is created, the agent reads issue 12, plans first, then shows the diff. Remember the line at the bottom: the agent is a fast assistant, not the engineer. You own every line you merge.

Instructor cue: Stress step five (test on hardware).
27

Agents inside GitHub

33:45–35:00 · 1 min 15 sGo to slide ↗

Agents can also work inside GitHub. In the example on the left, a student asks in a pull request: "@claude, why does the stall only happen on the left motor?" The agent looks at the files and pushes an explanation and a fix — but says "please test on the robot". Another teammate writes "@codex review" to ask Codex for an automatic review. Setting this up needs admin rights on the repository. The small file on the right is the rules file I mentioned: the board is an ESP32, the pin map is here, never change pins without asking. The agent reads it every time it runs.

28

Using AI responsibly

35:00–37:00 · 2 minGo to slide ↗

We have some ground rules for AI. One: you own it. You are responsible for every line you merge, whoever wrote it. Two: understand, then merge. Don't merge code you can't explain; if needed, ask the agent to explain it. Three: test on hardware. The agent can't see your robot and doesn't know the motor is overheating. Four: no secrets in prompts — never paste passwords, API keys or personal data. Five: be transparent. Say in the pull request what the AI did, and keep the Co-authored-by lines that agents add. The last card is this course's own policy: when AI help is allowed in this course.

Instructor cue: State your course policy clearly here; fill in the card on the slide beforehand if it is empty.

32

Where to click on GitHub

40:00–43:00 · 3 minGo to slide ↗

During the live demo, watch for four places. From the plus menu at the top right, I choose New repository. The name is hello-world, "Add a README" is ticked, Create repository. Now I open the branch menu on the Code tab, type readme-edits, and the branch is created. I open the README with the pencil icon and add a line about our robot; look at the Preview tab to see how the Markdown renders. I click Commit changes and write a short message. GitHub now shows a yellow banner with a Compare & pull request button; I click it, describe what I did, and click Create pull request. On the Files changed tab you see the diff: the green line is the one I added. Merge pull request, Confirm merge, and I delete the branch. main now contains the change. Everything we talked about today was in those three minutes.
