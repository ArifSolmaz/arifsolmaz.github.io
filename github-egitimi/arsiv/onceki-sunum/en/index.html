GitHub: What For, Why, How?

03

WHY DOES IT EXIST?

What problem does GitHub solve?

As a project grows, three questions get harder: Which file is current? Who changed what? Can we go back if something breaks?

Memory

It keeps project history. It answers “why did yesterday’s working thing break today?” with evidence.

Teamwork

Instead of getting lost in different copies of the same file, people share work visibly.

Visibility

Code, websites, documents, task lists and contributions become readable in one place.

Short definition: GitHub is an online workspace for project history, teamwork and sharing.

GitHub: What For, Why, How?

04

TWO DIFFERENT THINGS

Git and GitHub are different

GIT

Change history

  • Runs on your computer
  • Keeps older versions of files
  • Lets you try things and go back
  • Can record work without internet

Like a time machine for the project.

GITHUB

Online project hub

  • Shares the project online
  • Can publish a website
  • Tracks tasks, bugs and ideas
  • Helps you show your work and join open source

Like a shared desk for the project.

Git keeps history; GitHub makes that history shareable with a team, school, company or the world.

Why is it so important?

Because most serious digital work is now run as projects whose history can be seen, shared and reviewed.

PART 1 · WORK VALUE

Why does it matter in school and work?

1 · Team language

Software teams talk through saved notes, task records and change proposals. Knowing that language makes it easier to join a team.

2 · Work with evidence

Instead of only saying “I did it,” you can show what you did and when with history and explanations.

3 · Safe experiments

You try new ideas without breaking the main working version, and go back if needed. That makes mistakes less scary.

4 · Visible work

A GitHub profile shows not only the result, but also how you think and work.

5 · Standard tool

The same logic appears in school projects, companies, open source and personal websites.

Summary: knowing GitHub is not just knowing commands; it is knowing how to work visibly and in an organized way.

13

PART 1 · HABITS

What should stay out of GitHub

Secrets

Wi-Fi passwords, API keys, tokens. If they were uploaded publicly, treat them as leaked.

Build outputs

Compiled .hex and .bin files, .pio/, __pycache__/ — they can be rebuilt from source.

Huge binary files

Videos and large CAD assemblies make history heavy. Use separate storage or add them to a download page.

# .gitignore

.pio/

build/

*.hex

secrets.h

19

PART 2 · COLLABORATION

When two people change the same place

// firmware/main.ino

<<<<<<< HEAD

const float Kp = 1.4;

=======

const float Kp = 1.8;

>>>>>>> feature/pid-ayar

What happened? Two people changed the same line differently; Git cannot decide which one is right.

1 · Which value is right? Talk with the team or test on the robot.

2 · Remove the markers and keep the correct line.

3 · Save it and send it to GitHub.

Prevention: get the latest version often, keep trials small, and avoid editing the same file at the same time.

AI and GitHub

AI can help; GitHub keeps changes visible, discussable and under human control.

PART 3 · AI

Where can AI help?

It can help

draft

It can explain code, suggest small fixes, draft project descriptions and organize task ideas.

But not every suggestion is correct; control stays with you.

Why does GitHub matter here?

control

Changes made with AI become visible on GitHub: what changed, who reviewed it, was it tested?

So fast help does not mean uncontrolled change.

Setup and tool choice are not the point of this lesson; workflow and responsibility are.

GitHub: What For, Why, How?

25

PART 3 · WORKFLOW

A safer way to use AI

1  Start with a clear task

2  Try separately without breaking the main version

3  Ask for explanation and a plan first

4  Read every change before accepting it

5  Test on the real robot

6  Share it and let a human review it

Good request:

“The left motor stops at low speed. First explain possible causes. Then suggest a small fix. Show me what you changed.”

Understand first, apply second, share last.

An agent is a fast assistant, not the engineer. You are responsible for every line you join back.

PART 3 · BASIC RULES

Use AI responsibly

You are responsible

You are responsible for every line you join back, no matter who wrote it.

Understand first, then join back

If you cannot explain it, ask the agent to explain it, or do not join it back.

Test on hardware

The agent cannot see your robot. Run it on the real system.

No secrets in prompts

Never paste passwords, API keys or personal data.

Be transparent

In the change note, clearly say where AI helped.
